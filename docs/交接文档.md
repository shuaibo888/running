# 燃赛路跑微信小程序交接文档

## 1. 项目定位

燃赛路跑是面向公司赛事私域用户的微信小程序。产品以“持续记录运动、统一衡量消耗、激励长期参与”为核心，不只服务跑步用户，也覆盖其他运动方式。

首期目标是完成可真实使用的运动记录与激励闭环：微信一键登录或手机号验证码登录 → 完善必要资料与定位授权 → 开始运动 → 查看实时卡路里、配速、距离、时长与轨迹 → 暂停/继续 → 结束并由服务端校验保存 → 查看历史、累计成果、文化线路、城市足迹、里程碑和排行榜。

`lupao/` 是老板用 AI 生成并明确要求重点参考的视觉原型。正式产品应尽可能延续其橙色燃赛品牌、国风文化线路、卡路里第一视觉层级、勋章展馆和沉浸式运动页面，但需求、数据和安全规则以本文档及正式实现为准。

## 2. 核心指标

- **统一核心指标：消耗卡路里（kcal）**。不同运动最终都换算为卡路里，用于个人累计、里程碑和排行榜。
- 跑步专项指标：实时配速、运动距离、运动时长和运动轨迹。
- 累计指标：累计消耗卡路里、累计运动次数、累计运动时长、累计运动距离，以及运动覆盖城市数。
- 卡路里属于估算值，应保存计算方式和数据来源，并在产品中明确提示，不作为医疗数据。

## 3. 首期功能范围

### 3.1 用户与双登录方式

- 登录页必须提供两种并列可用的登录方式：微信小程序一键授权登录；手机号 + 短信验证码登录。不能把手机号登录只做成微信登录失败后的临时兜底。
- 微信小程序授权登录或手机号验证码登录后都建立同一种平台用户与 Sa-Token 登录态，后续运动、统计、成就和排行榜数据只关联平台用户 ID，不直接关联某一种登录方式。
- 平台账号以经过微信官方或短信验证码验证的完整手机号作为唯一归并依据。同一手机号无论先使用哪个入口，必须进入同一个平台用户，不能因为登录顺序不同再创建第二个账号。
- 维护昵称、头像，以及计算卡路里所需的必要身体信息；敏感信息遵循最小采集原则。
- 记录用户所属城市/省份，供地区排行榜使用。
- 微信一键登录按钮必须使用微信官方 `open-type="getPhoneNumber"` 能力。一次登录同时产生两种不同凭证：`uni.login` 的 `code` 用于后端 `code2Session` 识别微信身份；`getPhoneNumber` 回调的 `phoneCode` 用于后端调用微信手机号接口换取已验证手机号。两个 code 不得混用，手机号授权被拒绝时不创建账号，页面保留手机号验证码登录入口。
- 微信 `openid/unionid` 与运动档案分表保存：身份表只供登录服务使用，档案接口不得返回微信身份标识。
- 首版身份表只保存 `openid/unionid` 的 HMAC-SHA-256 摘要，不保存 `session_key`；手机号也使用服务端稳定密钥生成 HMAC 摘要，降低普通哈希被枚举反推的风险。该密钥不得提交 GitHub或随意轮换。若以后确定需要订阅消息，再单独设计可逆加密凭据存储、密钥轮换和授权撤销流程，不能为了预留功能先明文保存。
- 档案字段包括昵称、头像、性别、出生日期、身高、体重、常住省份和城市；用户 ID 只能取自服务端登录态，客户端无权指定或修改。
- 昵称、头像可以为空；当昵称、性别、出生日期、身高和体重齐全时档案才标记为完整。开始需要卡路里结算的运动前必须提示补齐必要信息。
- 身高、体重等资料允许后续修改，但每次运动结算仍需保存本次实际采用的体重/算法版本，不能因用户改资料而改变历史运动结果。

手机号验证码规则：

- 发送接口只接受格式正确的手机号；验证码不得写日志、不得返回给前端，默认 5 分钟内有效，成功登录或绑定后立即作废。
- 同一手机号 60 秒内最多发送一次，并设置单手机号、单 IP 的小时/每日上限；错误验证码必须限制尝试次数，防止暴力枚举。
- 开发阶段短信供应商 AccessKey、Secret、签名和模板 ID 按负责人要求写入后端配置文件；部署前必须移出版本库、迁入环境变量或密钥管理并完成密钥轮换。
- 手机号属于个人敏感信息。首版身份映射优先保存不可逆摘要；如运营后台确实需要联系用户，必须另行确认采集目的、展示脱敏和加密存储方案。

账号归并规则：

- `run_phone_identity` 是平台用户归并的主身份映射，`run_wechat_identity` 是附加登录凭证。微信授权取得手机号后先按手机号查找平台用户，再记录当前小程序微信身份；手机号验证码登录也按完全相同的手机号映射查找。
- 用户先用手机号验证码注册、后用微信授权同一手机号时，微信身份自动关联原账号；用户先用微信授权注册时，同一请求就创建手机号映射，之后短信验证码登录自动进入原账号。
- 正常登录流程不提供“登录后再手工绑定手机号”的步骤，也不要求微信用户进入个人中心补绑手机号。登录方式状态只用于告知，不承担账号合并操作。
- 只有完整且验证通过的手机号可以作为归并条件；不能凭昵称、头像、手机号尾号、设备、`openid` 或地理位置另行判断用户。

### 3.2 运动记录

- 跑步：开始、暂停、继续、结束运动。
- 运动过程中展示实时配速、距离、时长、轨迹和预估消耗卡路里。
- 结束后保存运动摘要与轨迹，并支持查看历史记录和单次详情。
- 其他运动：选择运动类型，记录时长及必要参数，统一计算或录入预估卡路里。
- 服务端校验异常数据，避免仅依赖客户端上报而产生明显作弊记录。

### 3.3 个人数据与成就

- 展示个人累计卡路里、运动次数、时长、距离和覆盖城市。
- 提供里程碑成就，例如累计卡路里、累计运动次数、累计距离、连续运动天数和覆盖城市数达到指定档位。
- 成就达成后保留解锁时间，避免重复发放。
- 正式积分由服务端统一记账：每日签到普通 +20，连续签到第 7 天起每日 +40；线路节点和成就按运营配置奖励，使用业务唯一键防止重复发放。
- 积分页展示真实余额、累计获得、连续签到和最近 50 条积分流水；积分商城不在首期范围，只展示“即将上线”。

### 3.4 排行榜

- 首期支持城市榜、省级榜，并预留全国榜。
- 以累计卡路里为主要排行指标，可按日、周、月和累计周期扩展。
- 排行榜必须明确地区归属、统计周期、更新时间、并列规则和异常数据处理规则。
- 运动发生城市与用户排行榜归属地是两个概念，不能直接混用。
- 排行榜地区冻结在每次运动创建时；用户修改常住地区只影响之后的运动，不得把历史成绩整体搬到新地区。

### 3.5 文化线路与城市足迹

- 重点参考 `lupao/` 中京杭大运河、万里长城和长征三条文化线路的视觉表达、节点推进、典故解锁和精神勋章设计。
- 真实运动里程可以累计到用户当前选择的虚拟文化线路；切换线路后只影响后续有效里程，历史累计不得丢失。
- 线路、节点、典故、勋章、奖励值和上下线状态由后端运营配置，不能长期硬编码在小程序页面。
- 城市足迹来源于有效运动轨迹，经腾讯位置服务解析为省、市、区及行政区划码；至少记录首次达成时间和最近运动时间。
- 线路节点、成就或积分奖励必须使用唯一业务键保证幂等，不得因重复提交运动结算而重复发放。

### 3.6 运动历史与异常恢复

- 支持运动记录分页、单次详情、轨迹回放、卡路里、距离、时长、平均配速和发生城市展示。
- 运动状态至少包含定位中、进行中、暂停、结束处理中、已完成和失败；结束操作必须防止重复提交。
- 当轨迹损坏或设备状态导致活动运动无法恢复时，用户可在明确二次确认后放弃记录；服务端将其幂等标记为 `FAILED` 并释放活动记录，但不得触发统计、线路、成就、积分、城市解析或排行榜。完成记录不可再放弃，客户端未上传轨迹在服务端确认成功后清除。
- 弱网、锁屏、前后台切换和异常退出时，客户端应保留未完成运动和待上传轨迹，重新进入后提示恢复或结束。
- 定位拒绝、定位精度不足、长时间无有效点、明显漂移和异常速度必须提示用户，并由服务端参与最终有效性判断。

## 4. 关键业务对象

- 微信身份映射（仅供服务端登录，不对小程序返回 `openid/unionid`）
- 手机号身份映射（平台账号归并主身份，仅供服务端登录，不返回原始手机号）
- 用户及用户身体信息
- 运动记录
- 运动轨迹点
- 运动类型与卡路里计算规则
- 用户累计统计
- 城市运动足迹
- 成就定义与用户成就
- 排行榜周期快照
- 积分账户与不可重复积分流水

## 5. 技术与产品边界

- 后端确定采用单体应用，不拆分微服务；业务代码按用户、运动、轨迹、统计、成就、排行榜和微信接入等领域模块组织，最终由一个主应用统一部署。
- 后端基础框架采用 RuoYi-Vue-Plus 5.6.2（官方 `5.X` 分支，基于 Spring Boot 3.5.15），统一使用 JDK 17、Maven、MySQL 8、Redis、MyBatis-Plus 和 Sa-Token；开发、构建与服务器运行环境均以 JDK 17 为准。
- 微信登录使用 JustAuth 校验 `uni.login` code，并由后端缓存微信接口调用凭证、消费 `getPhoneNumber` 的 phoneCode 换取手机号；手机号验证码使用框架已有 SMS4J 接入短信供应商。AppSecret、接口调用凭证、原始手机号和微信身份均不得返回小程序。若后续增加订阅消息等更完整微信能力，再评估引入 WxJava 小程序模块。
- 地图服务商确定为腾讯地图/腾讯位置服务。前端使用微信小程序原生地图组件展示当前位置、标记点和轨迹折线；定位坐标统一采用 GCJ-02。
- 腾讯位置服务主要承担逆地址解析、行政区识别以及后续可能的 POI/路线能力。开发期高权限 WebService Key 仅配置在后端配置文件中并由后端代理调用；不得下发小程序，也不得与小程序端受限 Key 共用，部署前迁为安全注入。
- 微信 `AppSecret` 开发期只写后端配置文件；小程序端只能持有可公开的 AppID 和经过来源/API 限制的腾讯地图客户端 Key，部署前将 AppSecret 迁为安全注入。
- 微信小程序端负责定位采集、轨迹绘制和实时展示；服务端负责持久化、统计、校验、成就判定和排行榜计算。
- 轨迹点不能按每个定位点同步写入数据库，应在客户端分段缓存、批量上传并做抽稀或压缩。
- 运动中断、弱网、退出小程序、定位拒绝和定位漂移都必须有明确的恢复或失败处理。
- 持续定位能力、后台运行时长及审核要求受微信小程序平台限制，开发前必须用真机验证，不能把完整 App 的后台运动体验直接视为小程序必然可实现。
- 城市足迹应由有效运动轨迹判定；地区排行榜归属应采用稳定、可审计的用户地区规则。
- 卡路里算法首期采用可解释的估算方案，后续可接入穿戴设备或更精细的运动模型。
- 跑步距离以过滤后的有效轨迹计算；卡路里需记录体重、运动类型、时长、MET/算法版本等计算依据。服务端复算并保存最终值，客户端实时值只是过程估算。
- 首版非跑步运动支持健走、骑行、跳绳、羽毛球、力量训练和瑜伽，使用 `MET × 体重(kg) × 时长(小时)` 结算并保存规则快照。手工时长无法验证真实性，因此计入个人累计、趋势和成就，但不进入地区排行榜。
- 腾讯逆地址解析不得对每个轨迹点调用，应在开始、结束、城市边界候选点或结算抽样时调用，以控制调用额度和响应延迟。

## 6. 首期暂不包含

- 赛事报名、计时芯片、赛事成绩同步和证书体系。
- 运动社交动态、群聊、私信和内容社区。
- 商城、积分兑换、广告和复杂会员付费体系。
- 智能手表、手环及第三方健康平台的深度接入。
- 专业训练计划、教练课程和医疗健康建议。

## 7. 开发前待确认事项

- 非跑步运动的 MET 参考值、最短/最长记录时长及后续是否增加强度档位，需由产品和运动专业人员复核后通过运营配置调整。
- 卡路里计算是否采集体重、年龄、性别等信息，以及隐私授权文案。
- 排行榜按用户常住地、报名地还是其他规则确定城市和省份归属。
- 日榜、周榜、月榜和总榜中，首期实际上线哪些周期。
- 是否需要轨迹分享、运动海报、好友邀请和企业私域运营入口。
- 小程序持续定位及后台运动能力的真机验证结论。
- 微信小程序主体类目是否具备前后台持续定位接口的申请资格；若不具备，首期必须明确只能在小程序保持可运行状态时采集，不能承诺完整 App 式后台跑步体验。
- 腾讯位置服务应用、开发 Key、生产 Key的申请人、额度、告警和密钥轮换负责人。
- 三条文化线路、历史典故、勋章文案和图片素材的版权及运营审核结论。
